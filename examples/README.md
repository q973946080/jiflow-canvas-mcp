# Examples — jiflow-canvas-mcp

Runnable, zero-cost examples for the standalone canvas MCP server. Everything here is
**fictional demo data**: canvas ids start with `canvas-demo-`, all URLs use the reserved
`example.invalid` domain and every token is a documented `demo-*` placeholder. No real user
data, assets, credentials or network calls are involved.

## Prerequisites

- Node.js >= 20
- `npm install` is only needed for the automated test suite (the MCP SDK devDependency);
  the server and these examples run with Node built-ins alone.

## Commands

| Command | What it does |
|---|---|
| `npm run seed:demo` | Recreates `examples/demo-store/` and `examples/auth.demo.json` from scratch (idempotent). |
| `npm run demo` | Spawns the real server over stdio and runs read → create → patch → connect → receipt → replay. |
| `npm run demo:conflict` | Starts two server processes, races one stale `expectedRevision`, asserts exactly one `CANVAS_REVISION_CONFLICT`, retries, and replays the winner. |

`npm run demo` seeds the store automatically when it does not exist yet; run `npm run
seed:demo` first for a deterministic revision 0.

## Files

- `seed-demo.mjs` — writes two fictional canvases (`canvas-demo-a`, `canvas-demo-b`) at
  revision 0 plus the fictional auth config. Tokens are stored only as SHA-256 digests.
- `lib/minimal-mcp-client.mjs` — dependency-free JSON-RPC 2.0 stdio client (spawn,
  initialize/initialized, request ids, notifications, timeouts, clean shutdown).
- `demo-client.mjs` — full MCP tool tour including an idempotent replay.
- `conflict-demo.mjs` — concurrent writers, CAS conflict, retry, cross-process receipt replay.

## Fictional tokens

These tokens are public demo fixtures. They are intentionally weak and must never be reused
outside the demo.

| Principal | Mode | Canvas scope | Token |
|---|---|---|---|
| `agent-writer-a` | `CANVAS_WRITE` | `canvas-demo-a` | `demo-writer-a-token` |
| `agent-writer-b` | `CANVAS_WRITE` | `canvas-demo-b` | `demo-writer-b-token` |
| `agent-reader` | `READ_ONLY` | `*` (all canvases) | `demo-reader-token` |

The auth config (`examples/auth.demo.json`) contains only `tokenSha256` digests. The raw
token is passed to the server through the `CANVAS_MCP_TOKEN` environment variable and is
never persisted, logged, returned by a tool or stored in a receipt.

## What the demos prove

`npm run demo`:

1. `initialize` negotiates a protocol version and reports `serverInfo.name =
   "jiflow-canvas-mcp"`, version `0.1.0`.
2. `tools/list` returns exactly nine `canvas_*` tools.
3. `canvas_list_canvases` is scoped to the token: writer-a only sees `canvas-demo-a`.
4. `canvas_read_canvas` returns the seeded fictional nodes and edges.
5. `canvas_create_node` / `canvas_patch_node` / `canvas_connect_nodes` each bump the revision by
   exactly one and use explicit `expectedRevision` values (CAS).
6. `canvas_read_receipt` returns the durable receipt for the create operation; its
   `payloadHash` matches the write result and no token appears in it.
7. Re-sending the same operation id with the same payload returns `replayed: true` at the
   original revision without a second write.
8. `canvas_list_receipts` returns the stored receipts newest first.

`npm run demo:conflict`:

1. Two independent server processes read the same revision `R`.
2. Both attempt a create with `expectedRevision: R`; exactly one succeeds and one gets
   `CANVAS_REVISION_CONFLICT` with `{expectedRevision: R, actualRevision: R+1}`.
3. The loser re-reads the canvas and retries successfully at `R+1`.
4. The winner's operation is replayed through the other server process (`replayed: true`,
   revision unchanged) and the loser's rejected operation has no receipt.

## Idempotency and safe retries

An operation is idempotent by `operationId`: replaying it returns the stored receipt
(`replayed: true`, revision unchanged) only when the payload is byte-identical after
canonical-JSON normalisation. Server-generated ids are fresh UUIDs on every call, so a blind
retry that omits `nodeId`, `edgeId` or `operationId` is a *different* payload and is
rejected with `CANVAS_OPERATION_PAYLOAD_CONFLICT` (correct per the documented contract). For retry-safe
writes, pass explicit `nodeId`/`edgeId` and `operationId` and reuse the exact same values on
retry. If a response is lost, recover the outcome with `canvas_read_receipt` (by
`operationId`) or `canvas_list_receipts` (by `canvasId`) before retrying.

`demo-client.mjs` demonstrates this: the create call supplies an explicit `nodeId` and
`operationId`, and the replay repeats both with an identical payload.

## Cleanup

`examples/demo-store/` is generated and git-ignored; `npm run seed:demo` recreates it at any
time. `examples/auth.demo.json` is regenerated by the seed script.

## Security notes

- No network calls: the server speaks JSON-RPC over stdio only.
- The server never writes logs to stdout; stdout is a pure protocol channel.
- Tokens travel only via the child process environment, never via argv.
- All store writes are CAS-guarded and atomic; a failed operation never changes the store.
